# 2. Project Identity

## Problem Statement

> Downscaling of weather forecast from Block level to Panchayat level: Inferring high-resolution plots/data/information from low-resolution plots/data/information/variables for agro-meteorological advisory services.

## Core Product

A responsive web/PWA platform that:

```text
Forecast / Reference Weather
        ↓
Spatial + Geographic Context
        ↓
Validated Localized Post-processing / Downscaling
        ↓
Panchayat-representative Weather Information
        ↓
Reliability / Uncertainty
        ↓
Agricultural Advisory
        ↓
Farmer / Officer Experience
```

## Core Product Statement

The system is a **weather intelligence and decision-support platform**, not simply a weather dashboard and not automatically an ML product.

---

# 3. Core Problem Understanding

The project should not be described as "inventing Panchayat weather."

The current ecosystem already includes increasingly localized official and commercial weather capabilities.

The meaningful engineering problem is:

> How can an available forecast field be transformed into more locally useful Panchayat-level information using geographic/observational context, while proving when the transformation helps and knowing when it should not be trusted?

The system should therefore be positioned as a:

**local forecast post-processing / downscaling / decision-support layer**

rather than a replacement for IMD's numerical weather prediction system.

---

# 4. Important Distinctions

These distinctions are mandatory.

## Forecast

A prediction issued before the valid weather time.

## Observation

A measurement recorded by a physical weather station/sensor.

## Reanalysis

A historical model reconstruction that assimilates observations.

## Derived Data

A value calculated from other data.

Examples:

- elevation difference
- terrain ruggedness
- interpolation
- bias correction

## Model Prediction

A value generated by the project's downscaling/post-processing model.

## Advisory

A decision-support output generated from weather information plus documented agricultural logic.

These must never be silently treated as interchangeable.

---

# 5. Current Scientific Hypothesis

The current working hypothesis is:

> A coarse/intermediate weather forecast can sometimes be improved at local/Panchayat locations using physical/geographic correction and, where justified by real data, residual statistical/ML correction. A reliability mechanism may then determine whether the localized correction should be trusted or whether the system should fall back to the authoritative/reference forecast.

This is a **hypothesis**, not a permanently accepted architecture.

The final method must be determined by experiments.

Possible final outcomes include:

- physical/statistical method only;
- statistical residual method;
- tree-based residual ML;
- probabilistic method;
- hybrid method;
- another scientifically justified approach.

If ML does not add value, ML must be removed from the core MVP.

# 18. Temperature Modeling Memory

Temperature is expected to have a stronger physical relationship with elevation than rainfall.

A lapse-rate-based correction is therefore an important baseline.

Conceptual form:

```text
T_corrected
=
T_reference
−
Γ × (z_station − z_model)
```

A standard lapse rate may be used as an initial baseline, but it must not be treated as universally optimal.

Potential comparison:

- fixed physical lapse rate
- locally estimated lapse rate
- simple bias correction
- statistical residual correction
- ML residual correction

The choice must be evidence-driven.

---

# 19. Rainfall Modeling Memory

Rainfall is substantially more difficult to downscale reliably at local scales.

Important factors may include:

- convection
- monsoon regime
- orography
- storm structure
- local spatial discontinuity

Do not assume a simple elevation rule will work uniformly.

A possible future formulation is:

```text
Rain occurrence
        ↓
Rain intensity given occurrence
```

But this is a hypothesis to test, not a permanent architecture.

Useful evaluation may include:

- MAE
- RMSE
- bias
- probability/risk measures where supported
- POD
- FAR
- CSI
- heavy-event detection

The sample count for heavy-rain events must be checked before making any claims.

# 21. Model Selection Memory

Model complexity is not a virtue by itself.

Selection principle:

> Choose the simplest method that demonstrates robust, reproducible, practically meaningful improvement on appropriate held-out data.

Potential outcomes:

### No ML

If a physical/statistical method performs sufficiently well.

### ML

Only if it provides measurable additional signal.

### Deep Learning

Only if data volume, spatial structure, compute, validation, and expected benefit all justify it.

Deep learning must never be included simply to make the SIH architecture sound advanced.

# 22. Reliability/Fallback Concept

Potential core system behavior:

```text
Reference Forecast
       ↓
Localized Correction
       ↓
Reliability Assessment
       ↓
 ┌───────────────┴───────────────┐
Reliable                       Unreliable
   ↓                               ↓
Serve localized              Fallback to
prediction                    reference/base
```

The fallback is intended to prevent the model from forcing a bad correction onto every Panchayat.

Potential reliability inputs:

- observation density
- nearest-station distance
- terrain context
- historical residual variance
- forecast lead time
- feature-space distance
- model disagreement
- out-of-distribution indicators

Potential uncertainty methods:

- conformal prediction
- quantile models
- prediction intervals
- ensemble spread

These are candidate approaches only.

---

# 23. Current Potential Differentiator

A candidate technical contribution has emerged:

**Reliability-aware local forecast correction with explicit fallback.**

The idea is not:

> "Our ML predicts better everywhere."

The idea is:

> "The system applies a local correction when evidence supports it and defers to the reference forecast when the correction is unreliable."

This differentiator is NOT considered proven yet.

It becomes a claimed core innovation only if:

- the correction itself is useful;
- the gate reliably identifies harmful corrections;
- useful corrections are retained;
- fallback frequency remains operationally useful;
- results survive held-out validation.

If those conditions fail, the differentiator must be revised or removed.

# 36. Useful vs Harmful Corrections

For a correction applied to a sample:

```text
Useful:
error is reduced

Harmful:
error is increased

Neutral:
change is negligible
```

This analysis is important because aggregate MAE can hide cases where a correction makes predictions materially worse.

A future reliability mechanism should be evaluated partly on whether it reduces harmful corrections.

# 57. What Counts as Scientific Success

Scientific success requires evidence that:

1. the input is a genuine forecast or clearly defined reference;
2. the target is a genuine observation or appropriately defined reference;
3. temporal leakage is prevented;
4. spatial leakage is controlled;
5. a strong baseline is included;
6. the method performs on held-out data;
7. improvements are meaningful, not only numerically tiny;
8. failures are visible;
9. the claim scope matches the validation scope.

---

## Phase 12 & 13 Scientific Blocker: Data Geometry
The Phase 12 validation experiment encountered a structural zero-elevation-difference issue. Phase 13 proved that this is because the Open-Meteo API returns the true SRTM elevation of the *requested* coordinate in its `elevation` field, not the snapped model grid point's elevation. While we can extract the true elevation difference by querying the snapped coordinates directly, Phase 13 revealed that the historical observation stations do not possess sufficient elevation gradients from their nearest snapped grid nodes (max < 80m, mean ~10m) to generate a statistically valid test of the B2 model. 
**Result:** B2 Production cannot currently be validated against historical observations. B2 remains EXPERIMENTAL — GO WITH LIMITATION. ML remains BLOCKED.
